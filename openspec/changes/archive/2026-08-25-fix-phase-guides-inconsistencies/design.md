## Context

Проект — учебные материалы по Roblox-разработке: план на 18–20 недель (`roblox-learning-plan.md`), 9 детальных гайдов в `phases/`, две шпаргалки. Аудит (см. proposal) выявил 6 серьёзных ошибок в примерах кода, 5 расхождений план↔фазы и ряд мелких несоответствий. Целевая аудитория — новичок, идущий по гайдам строго последовательно: любая ошибка в шаге блокирует прохождение.

## Goals / Non-Goals

**Goals:**
- Все примеры кода работают при последовательном прохождении фаз без правок со стороны ученика
- План обучения и файлы фаз согласованы: каждый пункт чеклиста плана покрыт гайдом
- Шаги внутри каждого гайда упорядочены: артефакты создаются до использования

**Non-Goals:**
- Переписывание гайдов на современный API везде (BodyVelocity → LinearVelocity остаётся с пометкой «устаревшее»)
- Добавление новых фаз или тем
- Правки шпаргалок (lua-shpargalka.md, roblox-shpargalka.md) — их разделы консистентны с фазами

## Decisions

### D1: Чекпоинты через `player.RespawnLocation` вместо ручного телепорта
Текущий код телепортирует игрока из `CharacterAdded`, борясь с авто-спавном движка. `RespawnLocation` — штатный механизм Roblox для этого сценария.
- **Альтернатива:** отключить SpawnLocation'ы полностью и оставить телепорт — отклонено: сложнее, ломает педагогику («SpawnLocation = чекпоинт»), теряется визуальная связь объекта и точки респавна.

### D2: Кнопку «Возродиться» связать с RemoteEvent, а не убирать
Вариант «упростить Фазу 5, убрав кнопку до изучения RemoteEvent» отклонён: экран смерти с кнопкой — естественный мини-проект, а разрыв «кнопка ничего не делает» хуже, чем короткая перемычка. Решение: в Фазе 5 кнопка скрывает оверлей + комментарий «подключим к серверу в Фазе 5.5»; в Фазе 5.5 практический пример переделывается с абстрактного ResetEvent на RespawnEvent → сервер вызывает `LoadCharacter`. Явно пометить как временное ограничение.

### D3: leaderstats создаёт один скрипт
Полный `DataStoreManager` (Фаза 6) забирает создание leaderstats себе; отдельный скрипт из Фазы 5 помечается как заменяемый: «в Фазе 6 удали этот скрипт — DataStoreManager создаст leaderstats сам». Загрузка данных идёт до создания leaderstats внутри одного PlayerAdded — гонка исчезает.

### D4: Расхождения план↔фазы решаем в пользу минимализма
Для каждого пункта плана без покрытия в фазе выбираем меньшую из двух правок:
| Пункт плана | Решение |
|---|---|
| Мёртвая зона (Фаза 3) | Добавить короткое упражнение в phase-3 (3 строки кода: Touched → Transparency + CanCollide=false) |
| Таймер + меню паузы (Фаза 5) | Скорректировать формулировку плана: убрать «меню паузы», таймер оставить опциональным заданием в phase-5 |
| Чат с вводом текста (Фаза 5.5) | Уточнить план: «сервер получает и выводит»; TextBox остаётся заданием со звёздочкой |
| Сохранение чекпоинта (Фаза 6) | Реализовать: чекпоинт хранится как номер в DataStore, загружается в PlayerAdded, восстанавливается в lastCheckpoint/RespawnLocation |

Критерий: реализуем за <15 строк кода в существующем стиле гайда — делаем; требует новой темы — переформулируем план.

### D5: SlowBrick — сохранять исходную скорость
`humanoid.WalkSpeed = 16` хардкодом хрупок (игрок мог быть уже замедлен другим кирпичом). Паттерн: прочитать значение при касании, восстановить его же после `task.wait(3)`; debounce per-brick оставляем, но добавляем проверку `humanoid.Health > 0`.

## Risks / Trade-offs

- [Правки кода не проверены запуском в Studio] → Каждый исправленный пример держать максимально близко к рабочим паттернам из официальных доков; ссылки на доки уже есть в гайдах
- [Увеличение объёма Фазы 5.5 из-за RespawnEvent] → Заменяем существующий пример ResetEvent, а не добавляем новый — объём нейтрален
- [Сохранение чекпоинта усложняет DataStoreManager] → Храним плоский словарь `{deaths, checkpoint}`, формат совпадает с существующим подходом
- [Пометки «устарело» у BodyVelocity могут смутить] → Уже есть в таблице ссылок; усилим одной строкой рядом с кодом
