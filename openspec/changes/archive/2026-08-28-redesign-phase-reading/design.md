# Design: навигация и ориентация внутри фазы

## Context

Сайт — статический Astro-курс (Astro 5, Content Collections, без UI-фреймворков).
Сейчас страница фазы рендерится через `PhaseLayout.astro` → `<Content/>` (весь `.md`
целиком) + прогресс-бар (привязан к чек-листу внизу) + prev/next. Глобальные стили и
клиентский скрипт прогресса живут в `BaseLayout.astro`; пер-step прогресс уже работает
(ключи `slug:step-N` в `progress.ts`), но виден только внизу страницы.

Жалоба пользователя: структура неудобна, «простыня», теряется желание заниматься.
Выбранный путь (A+B): дать **карту шагов** и **видимый по ходу чтения прогресс**.
Форм-фактор: вариант (a) — боковой sticky-rail на десктопе, сворачивающийся в
верхний чип на мобиле. Rail ведётся по заголовкам `## Шаг N`.

Ограничения: тема Solarized Light и шрифты не трогаем (оставляем как есть); контент
фаз (`.md`) не редактируем — только обёртка/разметка/скрипты; логику `progress.ts`
не меняем.

## Goals / Non-Goals

**Goals:**

- Sticky-блок сверху: «Фаза N · Шаг K/M» + fill = % прокрутки статьи.
- Боковой rail по `## Шаг N` (серверная генерация), scroll-spy подсветка текущего.
- Мобильное сворачивание rail в dropdown внутри sticky-блока.
- Три независимых слоя ориентации с разными знаменателями (позиция / % чтения / завершение).

**Non-Goals:**

- Изменение содержимого фаз и шпаргалок (`.md`).
- Смена темы/шрифтов.
- Изменение логики хранилища прогресса (`progress.ts`).
- Привязка rail к чек-листу (чек-лист остаётся отдельным счётчиком завершения).
- Интерактивный «пошаговый мастер» (показывать по одному шагу) — отложено.
- Тёмная тема / переключатель.

## Decisions

### D1. Rail генерируется на сервере из `phase.body`

В `src/pages/phases/[slug].astro` парсим `phase.body` регэкспом
`/^##\s+Шаг\s+(\d+(?:\.\d+)?)\s*:?\s*(.*)$/gm`, получаем `steps: {n:string, title:string}[]`
и передаём в `PhaseLayout` как проп. Rail рендерится как обычный `<nav>` — без мигания
до загрузки JS (в отличие от клиентского парсинга DOM).

*Почему:* контент не трогаем; серверный рендер надёжнее и SEO-дружественнее.
*Альтернатива:* клиентский `querySelectorAll('article h2')` — отвергнута из-за мигания
и дублирования уже имеющегося `phase.body` на сервере.

### D2. Sticky-блок = шапка + индикатор чтения, единый `position: sticky`

В `BaseLayout` оборачиваем `<header>` и новый индикатор в один sticky-контейнер
(`top: 0`, фон `--bg-soft`, тонкая тень, без layout-сдвига). Индикатор показывает
`Фаза N · Шаг K/M` (K/M — из scroll-spy по rail) и полосу заполнения = **% прокрутки
статьи** (scroll listener на `<article>`).

*Почему:* единый sticky-блок «красивее» и проще в вёрстке, чем две независимые
прилипающие зоны; % прокрутки даёт самое прямое «чувство движения» (пункт B).
*Альтернатива:* fill по чек-листу — отвергнута (дублирует нижний бар и не чувствуется
как движение при чтении).

### D3. Три слоя с разными знаменателями — это ок

- Rail + «Шаг K/M» отвечают «где я / что впереди» (дискретные шаги, 5–8 на фазу).
- Fill sticky-блока отвечает «сколько прочитал» (% статьи, непрерывный).
- Нижний чек-лист «Самопроверка X/N» отвечает «что усвоил» (7–19 пунктов, реальное
  завершение фазы, двигает существующий прогресс-бар).

Проверка по всем 12 фазам: заголовков `## Шаг` 5–8, чек-листов 7–19 — они
системно не совпадают, значит чек-лист это самопроверка, а не шаги. Поэтому
привязывать rail к чек-листу нельзя; разделение слоёв — осознанное решение.

### D4. Rail на десктопе, dropdown на мобиле

Вёрстка `<main>` на десктопе (≥900px): CSS-grid из двух колонок — rail (≈240px,
`position: sticky; top: <высота sticky-блока>`) + контент (max-width ≈680px).
Ниже 900px rail скрывается (`display:none`), а его элементы дублируются в sticky-блок
как `<details>`/выпадающий список «Шаг K/M ▾».

### D5. Scroll-spy и scroll-% — тонкий клиентский слой

В `BaseLayout` (рядом с существующим скриптом прогресса) добавляем:
- IntersectionObserver на heading'и шагов (`[data-step]`), поддерживаем множество
  «видимых» и выбираем верхний как текущий; обновляем «Шаг K/M» в sticky-блоке и
  класс `.current` на rail-элементе.
- scroll listener на `<article>`: `fill = scrollTop / (scrollHeight - clientHeight)`,
  записываем ширину `.reading-fill`.
- Клик по rail-элементу → `scrollIntoView` целевого heading; учитываем
  `scroll-margin-top` = высота sticky-блока + отступ.

### D6. Стили — продолжаем паттерн `BaseLayout`

Все новые стили — в `<style is:global>` `BaseLayout.astro`, на существующих
CSS-переменных Solarized (`--bg-soft`, `--border`, `--accent`, `--green`, `--muted`).
Rail: мягкий фон/бордер, номер-бейдж в кружке, `.current` — акцентный цвет/жирность,
пройденные (scroll-past) — приглушение. Без новых зависимостей.

## Risks / Trade-offs

- [Scroll-spy на краях: первый шаг «current» сразу, последний — только у самого низа]
  → принять; при скролле в самый верх показываем шаг 1, у низа — последний.
- [Изменение обёртки фазы может сдвинуть существующий прогресс-бар/prev-next]
  → prev-next и нижний чек-лист остаются в `<article>`, их вёрстку не трогаем; риск
  только визуальный, проверяем вручную.
- [Shiki/код не затрагивается] → риска нет; rail только навигационный.
- [Дублирование элементов rail в мобильном dropdown] → те же `steps` из пропа,
  второй разметкой; поддерживать синхронно с desktop-rail.
- [Страницы шпаргалок и `/plan/` не затрагиваются] → там rail не нужен.

## Open Questions

Нет — все решения приняты пользователем (вариант a, rail по `## Шаг N`, fill = % скролла,
единый sticky-блок header+bar).
